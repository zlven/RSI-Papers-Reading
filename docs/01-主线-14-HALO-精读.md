## 1. 研究背景与动机

**领域位置**：工业界对 2026 年 harness 自我改进浪潮的产品化回应。学术工作（Self-Harness、AHE 等）在基准上证明了可行性，但工程团队需要的是：**直接对生产环境中的真实 agent 轨迹**做同样的闭环，而不必自建整套评估基础设施。

**痛点**：
1. 学术方法绑定特定基准，生产团队无法复用；
2. 失败诊断与修复落地之间隔着"谁来改代码"的鸿沟——HALO 的答案是把修复交给编码智能体（coding agent）；
3. 自助式、本地化：桌面应用降低接入门槛（同时提供 inference.net 托管版）。

---

## 2. 核心 Insight 与理论依据

1. **生产轨迹 > 基准轨迹**：改进信号应来自真实使用分布；
2. **RLM 作为优化器**：用递归语言模型调用结构来处理"轨迹太长、单次上下文放不下"的诊断问题——与学术界"证据蒸馏"（AHE）、"弱点聚类"（Self-Harness）同构，但工程实现不同；
3. **诊断与修复分离**：HALO 产出诊断/改进提案，落地由编码智能体执行——与 MOSS 的"Implement 委托外部 coding-agent CLI"设计遥相呼应。

**理论依据**：无学术理论；方法论自觉（仓库自述为 "a methodology for building recursively self-improving agent harnesses using RLMs"）。

## 3. 方法详解

### 3.1 组成（按仓库）

- **HALO Desktop App**：本地运行完整循环（加载 demo 轨迹 → 运行 HALO → 用编码智能体 ship fixes）；
- **HALO-RLM 引擎**（Python 包，PyPI 分发）：核心优化循环；
- **Demo 工程**：演示如何为自己的 agent 搭 HALO 循环；
- **基准适配**：AppWorld 等公开基准的接入示例。

## 9. 批判性问题清单

1. **无公开评估协议**：与 AHE 的"可证伪契约"相比，HALO 用户得到的审计保证是什么？
2. **RLM 引擎与学术证据蒸馏的等效性**：长轨迹处理的正确性如何验证？
3. **生产轨迹的分布漂移**：用本周轨迹改出的 harness 下周是否仍有效——持续改进的稳定性无公开证据。
4. **修复执行外包给编码智能体**：与 MOSS 相同的外包结构，也意味着相同的归因问题——"自我"改进中外部模型的贡献占比几何？
