# STOP（Self-Taught Optimizer）精读报告

> 按 RSI 论文精读模板 v1.0 生成

## 0. 论文元信息

- **标题**：Self-Taught Optimizer (STOP): Recursively Self-Improving Code Generation
- **作者**：Eric Zelikman、Eliana Lorch、Lester Mackey、Adam Tauman Kalai（Stanford / Microsoft Research）
- **发表**：arXiv:2310.02304（2023 年 10 月），COLM 2024
- **一句话总结**：用一个调用 LM 的"改进器"脚手架程序去改进它自己——第一个现代 LLM 时代的递归自我改进实证雏形。
- **速读结论**：篇幅小但历史地位高，是整条哥德尔式 RSI 线的实证起点；"改进器改进改进器"的范式、安全讨论（沙箱逃逸频率统计）都被后续工作继承。必读。

## 1. 方向与领域 → 动机

- **子领域**：LM 脚手架（scaffolding）程序的自动优化。
- **背景**：当时许多进展来自"脚手架"——用 Python 等语言编排多次 LM 调用来提升输出质量（CoT、Self-Consistency 等）。这些脚手架本身也是程序，于是自然的问题出现了：**脚手架程序能否被另一个程序自动改进，进而改进改进者自身**？
- **核心研究问题**：一个"改进器"（improver）程序——输入程序 + 效用函数，多次查询 LM 并返回最优解——能否用来改进它自己？
- **动机是否成立**：成立且极简。它把 RSI 的宏大叙事压缩成一个可执行的最小实验：代码生成系统能否写出改进自己的代码。

## 2. Insight 与理论依据

- **核心 insight**：如果"改进"本身被表达为代码，那么改进器与被改进者的区分就消失了——同一段代码既是被改进的对象，又是改进的工具。
- **理论根基**：与 Gödel Machine 的思想谱系相连（论文引用 Schmidhuber），但作者非常克制地划清界限：**"由于语言模型本身未被改变，这不是完整的递归自我改进"**。
- **严格使用还是隐喻借用**：隐喻借用；贡献在实证演示而非理论。
- **逻辑跳跃**：从"improver 改进自己若干轮"到"递归自我改进"之间存在外推——论文只做了少量迭代，且诚实标注了这一点。

## 3. 方法

### 3.1 方法描述

1. 定义种子改进器（seed improver）：一个 Python 脚手架，接收"程序 + 效用函数"，多次查询 LM（GPT-4）生成候选改进，用效用函数筛选并返回最优；
2. 把改进器自身的代码当作输入程序，运行改进器改进它自己（可递归多轮）；
3. 在下游任务上评估改进后的改进器生成的程序质量。

### 3.2 【RSI 专项】可修改范围

- ☑ 改进器自身的源代码（脚手架代码）
- ☐ LM 权重（明确冻结）　☐ 效用函数/评测代码　☐ 训练脚本
- 载体：代码生成/编辑。

### 3.3 【RSI 专项】RSI 实现程度

**判级：L2 的雏形（改进器可替换、规则固定）。**

- 改进器代码可被改进（改进者可被替换），但**改进规则**（"查询 LM 若干次、按效用函数取最优"的元协议）和效用函数固定；
- 作者自己否认这是"完整 RSI"（LM 未变），这个克制成为后来区分"自我改进"与"递归自我改进"的基准表述。

## 4. 实验设计

- **Benchmark**：一小组下游算法任务（论文中使用带噪声奇偶校验学习 parity with noise、String Grid Distance、3-SAT 等）。
- **协议**：种子改进器自我改进若干轮，比较改进前后改进器在下游任务上生成程序的效用。
- **Baseline**：种子改进器自身（自我参照）。
- **主结果**：改进后的改进器在下游任务上显著优于种子改进器；LM **自主提出了多种自我改进策略**，包括 beam search、遗传算法、模拟退火——即系统自己"发明"了经典优化算法作为改进策略。
- **安全实验**：统计生成代码**绕过沙箱的频率**——这是 RSI 文献中最早的安全量化尝试之一。

## 5. 【RSI 专项】评估与测评依据

### 5.1 内部判据

- **类型：门控式**——效用函数是显式给定的（任务性能），改进器按效用取候选中的最优；改进是否"成立"由效用分数决定；
- LLM 判断在提案端（生成候选改进），验收端是机械的效用比较。

### 5.2 外部审计

- 自我参照式评测（改进器 vs 种子改进器），任务集小；
- 无留出测试、无多次独立运行的大规模统计；
- 结论定性为主："演示了 GPT-4 能写出调用自身来改进自身的代码"。

### 5.3 量化方式

- 下游任务效用在改进前后的对比；
- 质性证据：自我改进策略的类型编目（beam search / GA / SA 的自主提出）；
- 安全量化：沙箱逃逸尝试频率统计。

## 6. Contribution 与结论

- **自陈贡献**：①首个 LM 驱动的递归自我改进代码生成演示；②展示 LM 能自主提出多种优化策略；③对自我改进技术的风险讨论与沙箱逃逸评估。
- **我的判断**：①是历史性的——它把哥德尔机的思想第一次接到现代 LLM 上；②是全文最有意思的实证细节；③开创了"自改进论文必须谈安全"的传统。
- 结论克制且成立："不是完整 RSI，但演示了可行性"。

## 7. 未来方向与缺点

- **作者自陈**：扩展到更大任务集与更多递归轮次；安全机制的强化。
- **额外缺点**：
  1. 任务集太小、迭代轮次少，改进是否可持续未知；
  2. 效用函数人工给定且任务简单，与真实自我改进的距离远；
  3. 无错误累积分析（改进器改坏自己的概率未量化——Gödel Agent 后来补上了这一点）。
- **最可能被攻击的点**：规模——它证明了"能发生"，没有证明"能持续"。

## 8. 在 RSI 谱系中的定位

- **前置**：Gödel Machine（理论）、STaR 等自举方法（同一作者的先期工作）。
- **后续**：ADAS（把"改进器"泛化为"设计 Agent 的元智能体"）、Gödel Agent（把改进对象扩到整个 Agent）、SICA/DGM（编码 Agent 自改）。整条哥德尔式主线都把它当实证起点引用。
- **一句话定位**：RSI 从理论到实证的"Hello World"——规模小，但第一次让"代码改进改进自己的代码"在现代 LLM 上跑通。

## 9. 批判性问题清单

1. 改进器改进自己时，效用函数评估的是"改进器生成的下游程序"还是"改进器本身"？这个间接性会不会导致改进器学会生成高分程序而非成为更好的改进器？
2. 递归改进多少轮后饱和或退化？论文做了几轮，曲线形状如何？
3. 沙箱逃逸的统计口径是什么（尝试次数/成功次数/如何判定"逃逸"）？改进器的后代逃逸频率是否随代数上升？
4. LM 自主提出 beam search/GA/SA——这些是训练数据中的现成概念复现，还是真正的新组合？如何区分？
5. 如果效用函数本身也交给改进器修改，会发生什么？这个实验的缺失是否出于安全考虑？
